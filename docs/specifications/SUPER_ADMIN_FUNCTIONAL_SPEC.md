# SUPER ADMINISTRATOR

## Super Admin Portal — Complete Functional Structure

The **Super Admin Portal** is the organization-wide control layer of the Science on Wheels platform. It provides the Super Administrator with complete visibility and administrative control over the organization's regions, users, mobile laboratories, schools, curriculum, resources and operational activities.

The portal should be designed around four fundamental responsibilities:

> **Configure → Control → Monitor → Analyse**

The Super Administrator establishes the organization's structure and master data, controls users and access, monitors activities performed by Regional Administrators and Field Staff, and uses consolidated operational data for reporting and decision-making.

The Super Admin has organization-wide visibility. However, this does **not** mean that the Super Admin performs every operational activity. Routine field activities such as attendance recording, equipment scanning, experiment execution and inventory consumption remain with the appropriate operational users. This separation preserves accountability. Pasted markdown(20260928-070626)



---



# 1. DASHBOARD

The **Dashboard is the entry point to the Super Admin Portal**. It should function as an organization-wide operations command center rather than simply displaying decorative statistics.

When the Super Administrator logs in, the dashboard should immediately provide a consolidated view of the current state of the organization.

The dashboard should combine information generated by all other sections of the platform.

### Organization overview

The dashboard should show the current organizational status through indicators such as:

- Total Regions
- Active Mobile Laboratories
- Active Field Staff
- Schools Covered
- Students Reached
- Sessions Completed
- Sessions Pending
- Inventory Alerts

These figures should be **calculated from live system data**, rather than manually entered values.

### Live operational view

The dashboard should also provide a map-based view of the organization's mobile laboratories.

For each laboratory, the Super Admin should be able to understand:

- where the laboratory currently is
- which region it belongs to
- whether it is travelling, at a school, returning or offline
- when its location was last updated
- which route it is following
- which school it is associated with for the current operation

For example:

ML-001 → Moving

ML-002 → At School

ML-003 → Returning

ML-004 → Offline

The intended architecture specifically defines current location, last update, lab status, region, route and destination as information visible on this organization-wide map. Pasted markdown(20260928-065611)

### Alerts

The dashboard should bring operational conditions requiring attention to the Super Admin instead of requiring them to manually inspect every module.

Examples include:

- equipment discrepancies
- low inventory
- laboratory offline
- missed visit
- delayed session
- equipment damage
- vehicle issue
- unsynchronized field data

Therefore, the dashboard acts as the **first-level monitoring layer** of the entire platform.

# 2. ORGANIZATION

The **Organization** section defines the structural foundation on which the rest of the system operates.

Everything else in the platform depends on knowing:

> **Which region does something belong to?**

Therefore, this section should be managed centrally by the Super Administrator.

## 2.1 Regions

The Super Admin should be able to create and maintain all operational regions.

For every region, the platform should maintain information such as:

- Region name
- State
- administrative geography
- assigned Regional Administrator
- associated schools
- associated laboratories
- associated Field Staff
- operational status

The Super Admin should be able to:

- create a region
- edit region information
- activate/deactivate a region
- view all regions
- assign a Regional Administrator
- change Regional Administrator assignment
- view region-level performance

A Regional Administrator should only operate within their assigned region. The Super Admin retains organization-wide visibility and control. Pasted markdown(20260928-070626)



---



## 2.2 Geography

Geography should provide the hierarchy required to organize schools and operational coverage.

The system's existing structure follows:

State

  ↓

Region

  ↓

District

  ↓

Block

  ↓

School

This hierarchy is important because it allows the platform to associate schools, people, laboratories and operations with their appropriate geographical scope. The current system already models State → Region → District → Block → School. Pasted markdown

The Super Admin should therefore be able to maintain this geographical master data and ensure that schools and regional operations are associated with the correct locations.



---



## 2.3 Organization Settings

This area contains organization-wide configuration that affects the operation of the platform.

It should contain settings that apply across the entire organization rather than settings belonging to a particular region.

The important principle is:

> **Organization-level configuration is controlled centrally and should not be independently changed by Regional Administrators.**



---



# 3. PEOPLE & ACCESS

The **People & Access** section controls who can enter the platform, what they are allowed to do, and what organizational data they are allowed to access.

This is not simply a list of users.

It is the platform's **identity and access-control layer**.

The access structure should work conceptually as:

USER

 ↓

ROLE

 ↓

PERMISSIONS

 ↓

DATA SCOPE

The current architecture already represents Users, Roles, Permissions and role assignments as separate entities. Pasted markdown



---



## 3.1 Regional Administrators

The Super Admin creates and manages Regional Administrator accounts.

When creating a Regional Administrator, the system should establish:

Person

   +

User Account

   +

Role

   +

Assigned Region

   +

Permissions

   =

Regional Administrator

The Super Admin should be able to:

- create the account
- edit personal information
- assign a region
- change the assigned region
- activate/deactivate the account
- lock/unlock the account
- reset credentials
- view login activity
- view account activity
- view operational activity

A Regional Administrator must not be able to create another Regional Administrator. That authority remains with the Super Admin. Pasted markdown(20260928-070626)



---



## 3.2 Field Staff

The Super Admin should also be able to manage Field Staff accounts at organization level.

The account should contain information necessary for operational assignment, such as:

- identity
- contact information
- role
- assigned region
- availability/status
- assigned laboratory where applicable
- account status

The Regional Administrator then handles the **day-to-day operational assignment** of Field Staff within their region.

This creates a clear distinction:

SUPER ADMIN

Account + Role + Organization Access

              ↓

REGIONAL ADMIN

Operational Assignment

              ↓

FIELD STAFF

Field Execution



---



## 3.3 Roles

The Super Admin controls the platform's defined roles.

For the current intended architecture, the principal roles are:

- Super Administrator
- Regional Administrator
- Field Staff

The role determines the user's operational responsibility.



---



## 3.4 Permissions

Permissions determine exactly what a role is allowed to do.

For example, a user may have permission to:

- view schools
- create schools
- edit schools
- view laboratories
- assign staff
- view inventory
- approve a workflow
- generate reports

The platform should not rely only on frontend hiding of buttons. The backend/API must enforce these permissions as well.



---



## 3.5 Account & Security Management

Super Admin should control the account lifecycle:

Created

   ↓

Activated

   ↓

Active

   ↓

Locked / Suspended

   ↓

Deactivated

The portal should provide appropriate account-management actions while maintaining an audit record of important changes.



---



# 4. MOBILE LABORATORIES

The **Mobile Laboratories** section maintains the organization's complete laboratory/vehicle operational structure.

The Super Admin should have organization-wide visibility of every laboratory.

For each laboratory, the platform should bring together:

Laboratory

 ├── Region

 ├── Vehicle information

 ├── Assigned staff

 ├── Equipment

 ├── Inventory

 ├── Maintenance

 ├── GPS

 ├── Routes

 └── Operational history

The intended system specifically assigns Super Admin responsibility for registering laboratories, assigning them to regions, transferring them, viewing staff, equipment, inventory, maintenance, GPS, travel history, utilization and operational status. Pasted markdown(20260928-070626)



---



## 4.1 All Labs

This provides the organization-wide laboratory directory.

The Super Admin should be able to filter and search laboratories by:

- region
- status
- assigned staff
- operational condition
- current location



---



## 4.2 Lab Details

Selecting a laboratory should open its complete operational profile.

The profile should bring together:

- laboratory identity
- assigned region
- current status
- assigned staff
- equipment
- inventory
- maintenance
- current GPS location
- route information
- operational history

This prevents the administrator from having to open separate modules simply to understand the state of one laboratory.



---



## 4.3 Assignments

Super Admin should be able to view and manage organization-level laboratory assignments.

Examples:

Lab → Region

Lab → Field Staff

Lab → Equipment

Lab → Inventory

A transfer from one region to another should create an auditable administrative event.



---



## 4.4 Maintenance

The laboratory's maintenance information should be available to the Super Admin, including maintenance status and service history.

This allows the organization to identify laboratories that are unavailable or approaching scheduled maintenance.



---



## 4.5 GPS / Location

The Super Admin should have organization-wide visibility into laboratory location information.

This should include:

- current location
- last update
- movement
- route
- school destination
- travel history
- offline status

The actual GPS collection mechanism belongs to the production implementation; the Super Admin portal consumes the resulting location information.



---



## 4.6 Utilization

The system should consolidate laboratory usage information so the Super Admin can understand:

- number of trips
- number of sessions
- operating hours
- idle time
- active/inactive laboratories

This data later feeds organization-wide analytics.



---

# 7. RESOURCES

The **Resources** section controls the physical resources required to operate the laboratories.

There is an important distinction between **master definitions** and **physical resources**.

### Equipment Master

Defines what an item is.

### Actual Equipment

Represents the physical item.

### Inventory

Tracks consumable quantities and transactions.

The existing design already follows this separation. Pasted markdown(20260928-065611)



---



## 7.1 Equipment Master

Super Admin defines equipment categories and master information.

Example:

Digital Microscope

Category: Laboratory Equipment

Unit: Piece

Trackable: Yes

QR/Barcode: Required

Minimum Stock: 2

The master definition can then be used consistently across all regions and laboratories.



---



## 7.2 Consumables

Consumable resources should be maintained with information such as:

- item
- category
- unit
- stock requirements
- minimum stock
- reorder level
- status

This allows the platform to generate low-stock conditions.



---



## 7.3 Inventory

Super Admin needs organization-wide visibility of inventory, while day-to-day regional allocation and field consumption remain with the operational roles.

The system should therefore be able to show:

Organization

 ↓

Region

 ↓

Laboratory

 ↓

Item

 ↓

Opening Stock

 ↓

Receipts

 ↓

Transfers

 ↓

Consumption

 ↓

Adjustments

 ↓

Current Stock

The current system already models inventory transactions including receipt, issue, return, transfer, adjustment, damage, loss and consumption. Pasted markdown



---



## 7.4 Maintenance

Resources requiring maintenance/calibration should retain their relevant maintenance information.

For equipment this may include:

- maintenance date
- calibration date
- warranty
- condition
- replacement status



---



## 7.5 Resource History

Every important movement should be traceable.

For example:

Equipment

 ↓

 ↓

 ↓

 ↓

Maintenance

## 8.2 Schedules

        ↓

Alert

        ↓

        ↓

## 9.3 Activity

Activity provides a chronological view of important system actions.

Inventory transferred

Lab reassigned

## 9.4 System Health

This is an area where the **final production requirements need to be defined separately from the current prototype**, rather than claiming that the existing build already provides all of it.

# 11. SECURITY & AUDIT

This is the final control layer of the Super Admin portal.

It answers:

> **Who accessed the system, what did they do, what changed, and when?**



---



## Audit Logs

Important actions should create an immutable audit record.

For example:

USER CREATION

PERMISSION CHANGE

REGION CHANGE

LAB REASSIGNMENT

EXPERIMENT MODIFICATION

INVENTORY ACTION

ACCOUNT DEACTIVATION

Each record should retain the actor, action, affected entity, timestamp and relevant change information.

The source explicitly requires audit records for login/logout, user creation/deactivation, permission changes, region changes, lab reassignment, experiment modification, inventory actions and other important administrative changes. Pasted markdown(20260928-065611)



---



## Login Activity

Super Admin should be able to review account access activity, including successful and relevant failed access events where implemented.

This helps identify:

- unusual access
- repeated failed logins
- inactive accounts
- suspicious account activity



---



## Permission Changes

Changes to access control should themselves be auditable.

For example:

Regional Admin

Old Region: Nagpur

New Region: Pune



Changed By: Super Admin

Timestamp: ...

The same applies to role or permission changes.



---



## Security Events

Security-related events should be centralized for administrative review.

The production implementation should additionally establish the appropriate authentication, authorization, session/token, secrets, rate-limiting, logging, backup and incident-handling controls.
